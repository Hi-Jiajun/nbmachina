# M1-4 实测报告 · 打击乐层（底鼓 / 军鼓 / 踩镲）

任务书：`nbforge-m1-4.md`（M1 第 4 条）。数据：`build/styx_helix_full.wav`（mono 44.1kHz，281.4s）
与现有谱面 `build/notes_recovered.csv`（M1-3 之后：2805 颗音、撞格 0）。

**一句话结论**：三条频带（40–120Hz / 150–400Hz / 6–16kHz）的谱通量取峰 + 攻击处**频谱形状**判别，
在自己合成的三类鼓点上 **30/30 全部检出、分类 100%、对齐中位 ≤2ms**（三类各 10 次）；
在真实混音上默认口径检出 **138 个事件**（底鼓 14 / 军鼓 82 / 踩镲 42），吸附到 0.12s 谱面网格的
偏移中位 **5.6ms**、|最大| 12.9ms，与 M1-3 的音频起音表（1829 个起音）对齐中位 **13.9ms**。

但有两句话必须先说（详见 §3.6 与 §3.5）：

1. **这份音频源几乎没有 6kHz 以上的能量**——6–16kHz 只占总能量 **0.31%**，逐帧占比中位数 **0.000%**
   （p99 13.0%）。也就是说这台机器的"踩镲带"在这个源上基本是空的：42 个"踩镲"只来自最响的那些
   高频瞬态，**不能当成一条完整 hi-hat 轨**。这是音频源的问题（`DISCUSSION-C-music.md` §1、§7.1
   已经建议重做音源），不是检测器能补回来的。
2. **军鼓在这台机器上没有对应格**（本机只有 `stone→basedrum` / `glass→hat` 两组打击乐方块）。
   默认把军鼓降级成 basedrum（row 0），并逐条记进 `degradations[]`——82 条降级明细。

并且：**这一层不接进机器**（播放器只认 harp/bass，`src/emit/datapack-playback.mjs` 的
`soundName()` 只映射这两种）。接线要改 `src/emit/*`，按任务书分工由**根代理**做；本任务只交付
`build/percussion.csv` + 本报告（接线清单见 §5）。

## 3. 口径与实测（以及两处改过的判断）

### 3.1 三条带与窗长：1024→2048（这是一个真 bug，不是调参）

第一版按"抓瞬态要用短窗"选了 1024 点（bin = 43Hz）。实测发现 40–120Hz 这条带**只剩 2 个 bin
（86–107Hz）**——底鼓 45–60Hz 的基频整个落在带外，检到的是"80Hz 以上那半截"。改成 2048 点
（bin = 21.5Hz）后是 4 个 bin（43/65/86/107Hz），才是任务书写的那条带；snare 带从 6 个 bin 变
12 个（172–387Hz）。同一段音频、同一套闸门下的对照：

```
窗 1024（kick 2 / snare 6 / hat 232 bins）：事件 225｜{"kick":42,"snare":149,"hat":34}｜闸门拦下 10691
窗 2048（kick 4 / snare 12 / hat 465 bins）：事件 138｜{"kick":14,"snare":82,"hat":42}｜闸门拦下 9496
```

代价是时间分辨率变粗（窗长 46.4ms），但 16 分格是 0.12s，仍远大于窗长——单测里
"连续 16 分格（0.12s 一个踩镲）16 下至少认出 13 下"就是为这条代价设的。

### 3.2 通量峰提前量标定：`latencyFactor = 0.8`

加窗谱通量的峰出现在真实起音**之前**，提前量与窗长成正比（M1-3 在钢琴点击上实测 0.5–0.7×窗长）。
在 2048 点窗上用**合成的三类鼓点**逐类标定（每类 10 次取中位）：

| 补偿 | kick | snare | hat | 说明 |
|---|---|---|---|---|
| 0.5×窗长 = 23.2ms | −14.3ms | −14.8ms | −12.2ms | 三类一致地"补少了" |
| **0.8×窗长 = 37.2ms** | **−0.4ms** | **−0.9ms** | **+1.7ms** | 默认值；最大偏差 ≤3.5ms |
| 0.9×窗长 = 41.8ms | +4.2ms | +3.8ms | +6.3ms | 开始过补，且有一类判错 |

比 M1-3 的 0.5–0.7 偏大，原因是打击乐的起振比钢琴点击更陡，通量峰更靠前。

（顺带一个坑：`latencyFactor = 0` 时合成轨道**一个事件都检不出**——因为第三道闸门
"攻击处 30ms 窗 RMS ≥0.01"是在**补偿后**的时刻上量的，不补偿就会量到起音之前的静音段。
这不是 bug，但说明这个闸门依赖时间补偿，两者必须一起改。）

### 3.3 判别分数为什么是"乘法"（两版实测的教训）

一个攻击要判成哪一类，用两块证据：**哪条带看到了它**（该带归一化通量）与**频谱形状像谁**
（五段能量占比 + 150–6000Hz 谱平坦度）。第一版写成加权**加法**，真实数据上 76% 的事件被判成军鼓。
两个原因，都在实测里：

1. **带内通量是按每条带自己的最大值归一化的**，所以一条几乎没能量的带（本曲 6–16kHz 只占 0.31%）
   里，底噪起伏也能拿到接近 1 的通量——只看通量，噪声就是"踩镲"。
2. **军鼓那一项天然占三个频段**（低/中/高三路里它取"中"），加法下它的分数系统性偏高。

改成 `分数 =（带通量 ^ 0.5）×（该类的形状项）` 之后：两块证据**必须同时成立**（空带里的假峰
乘上"高频占比 ≈0"直接归零），三类的形状项又都取自**同一组三路占比**（低 40–120 / 中 150–1500 /
高 6–16kHz，相加 = 1），可比。合成样本上分类 100%，真实数据上三类的判据中位数也自洽（§3.5）。

### 3.4 绝对超额闸门与工作点敏感性

只靠"突出度 ≥1.5×局部均值"是不够的：军鼓 0.09s 的噪声衰减里，随机起伏很容易做到 2–4 倍局部均值
（第一版在合成的军鼓尾巴上产出 4–6 个假峰）。所以再加一道**绝对**闸门：
`excess = 归一化通量 × (1 − 1/突出度)` = 峰比 ±100ms 局部均值高出的**绝对量**。

合成样本上"事件数正好 30/30 且分类 100%"的区间是 `0.15 ≤ minExcess ≤ 0.45`，默认取中点 **0.3**：

| minExcess | 合成：事件/30 | 合成：分类 | 真实：事件 | 真实：底鼓/军鼓/踩镲 |
|---|---|---|---|---|
| 0 | 69 | 73.9% | 5033 | 1855 / 3132 / 46 |
| 0.05 | 51 | 84.3% | — | — |
| 0.1 | 33 | 97.0% | 1118 | 474 / 596 / 48 |
| 0.15 | 30 | **100%** | 509 | 138 / 328 / 43 |
| 0.2 | 30 | **100%** | 280 | 51 / 187 / 42 |
| **0.3（默认）** | **30** | **100%** | **138** | **14 / 82 / 42** |
| 0.35 | 30 | 100% | 101 | 8 / 51 / 42 |
| 0.5 | 30 | 96.7% | 32 | 1 / 1 / 30 |

读法（这段是**工作点**，不是"对错"）：闸门越松，事件越多、越可能混进别的乐器的攻击
（底鼓那一列从 474 掉到 8 就是这个效应——它的攻击在密集混音里相对更不明显）。默认 0.3 是能给出的
**最有依据**的取值（合成上双侧都留了余量），但真实数据没有标注、无法给准确率，所以：
`npm run arrange:percussion -- --min-excess 0.2` 可以得到更密的打击乐层（280 条），
接线阶段想"更有劲"就往 0.2 走，想"只留重音"就往 0.35 走——**听感最终要用人耳验收清单里第 7 条
（每段重音与鼓点一致）来定**，那一步属于接线。

### 3.5 真实数据：判据中位数、时间分布、节拍规律

三类的判据（默认口径，中位数）——用来回答"这些标签看起来合理吗"：

| 类别 | n | 谱重心 | 三路占比（低/中/高） | margin | 强度 |
|---|---|---|---|---|---|
| 底鼓 | 14 | 359Hz | **0.77** / 0.19 / 0.00 | 0.139 | 0.400 |
| 军鼓 | 82 | 1169Hz | 0.02 / **0.89** / 0.02 | 0.226 | 0.406 |
| 踩镲 | 42 | 3699Hz | 0.00 / 0.31 / **0.68** | 0.453 | 0.699 |

（底鼓的谱重心 359Hz 偏高，是因为这个窗里同时装进了低频本体与宽带拍击——它仍远低于军鼓的 1169Hz。）

时间分布（每 30s 一格）：`0-30s:8 30-60s:4 60-90s:7 90-120s:15 120-150s:11 150-180s:3
180-210s:7 210-240s:9 240-270s:19 270-300s:55` —— **末段 270–300s 占了 55/138（40%）**，
密度前后不均（前 150s 只有 45 条）。这与"末段编曲最满、混音最响"一致，但也意味着这条打击乐层
**前半段偏薄**——想做成"整曲都有鼓"的听感，得先解决音源与工作点（§3.4）。

节拍规律（±30ms 容差，扫相位取最佳）：

```
网格 0.48s：最佳相位 0s → 68/138 = 49%（随机水平 13%）
网格 0.96s：最佳相位 0s → 31/138 = 22%（随机水平 6%）
```

即检出的事件有近一半精确落在原曲的拍点上（随机只有 13%），与 `DISCUSSION-C-music.md` §4.3
"0.96s 的 onset 自相关最高（0.70）"的结论方向一致。

### 3.6 音频源审计：6–16kHz 只有 0.31%

对整段音频逐帧（2048 点 Hann 窗、50ms 步长，5628 帧）统计能量占比：

```
40-120Hz 37.15%｜150-400Hz 9.12%｜400-1500Hz 27.84%｜1500-6000Hz 11.71%｜6000-16000Hz 0.31%｜16000-20000Hz 0.00%
逐帧 6-16kHz 占比：p50 0.000%｜p90 0.429%｜p99 13.004%｜max 28.544%
```

两件事必须写下来：

1. **高频被切掉了**（典型的低码率/低通源：1.6 万 Hz 以上 0.00%、中位帧 6kHz 以上 0.000%）。
   所以"踩镲 >6kHz"这条带在本源上基本无料可检，42 个踩镲是"p99 以上那些帧"，**不是一条 hi-hat 轨**。
   要真正的踩镲层，先换音源（`DISCUSSION-C-music.md` §7.1），或用更低的带（4–10kHz）重做一次口径标定。
2. **低频被贝斯占满**（40–120Hz 占 37.15%）。虽然谱通量只看"变化"，持续的贝斯不会持续刷出通量
   （逐带归一化通量的 p50 只有 0.008），但底鼓与贝斯在**同一频段**上物理不可分，所以"检出的底鼓"
   里必然混有低音音符的攻击——默认口径下底鼓只有 14 条（保守），也是同一件事的另一面。

## 5. 接线清单（**这一层不接进机器**）

按任务书分工，本任务只交付 CSV + 报告。要真正听到打击乐，根代理需要做下面几件事（都不在本次改动范围）：

1. **播放器只认 harp/bass**：`src/emit/datapack-playback.mjs` 的 `soundName()` 把非 bass 一律当 harp，
   `INSTRUMENT_VOICE` 里 basedrum/hat 已经登记为 `perc` 声部，但取音色/取坐标的分支要补；
   监听模式（`#mon=1` 时按玩家脚下放音）也要一起处理。
2. **摆块**：`src/emit/note-blocks.mjs` 的 `DECK_BLOCK` 只有 `harp/bass` 两项，要补
   `basedrum → minecraft:stone`、`hat → minecraft:glass`；`noteBlockOf()` 目前强制
   `instrument=harp|bass`，也要按 `PERCUSSION_CELLS[kind].instrument` 走。
3. **撞格**：默认口径下 138 行中有 **0 行**落在现有谱面已占用的格（已实测），所以直接并入不需要取舍；
   但**宽松口径会有撞格**，并入时要注意 `dedupe.mjs` 的声部优先级是
   `melody > bass > inner > perc`——**perc 最低，撞格时打击乐会被静默丢掉**。要么让打击乐优先，
   要么在并入前用本模块的 `stats.mergedSameCell` 显式记录丢掉哪些。
4. **刻率**：打击乐与旋律共用 `step×12` 刻的网格（100 tps 精确），不需要新的时间轴；
   20 tps 模式下 `tick-map.mjs` 会把它折到最近的刻，实测偏移中位 5.6ms，不需要额外处理。
5. **验收**：接完线跑 `npm run verify`（客观分不应下降——`score.mjs` 只统计 harp/bass 的起音/八度/chroma，
   打击乐不参与打分）与人耳清单第 7 条"每段重音与鼓点一致"。

已实测的接线前风险（如实列出）：

1. 音源 6kHz 以上几乎是空的 → **踩镲层只是零星高频瞬态**，别指望它像原曲的 hi-hat（§3.6）。
2. 底鼓与贝斯同频段 → 默认口径只留 14 个底鼓（保守），且末段偏密、前半段偏薄（§3.5）。
3. 同时刻的底鼓+军鼓只出一个事件（两者在本机本来就占同一格 row 0，不丢信息）；
   如果要"底鼓+军鼓各一格"，那需要**机器改造**（再加一行与一组方块），不是这一层能解决的。
