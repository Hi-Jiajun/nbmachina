# M3-37 · 音符盒触发位矩阵：为什么现在走的是自研演奏器（2026-09-19）

**起因（用户原话）**："这个mod不应该是对音符盒的增强吗？为啥不走音符盒？那不就成播放制作好的音频了嘛？"

先把两件事分开：

- **不是"播放做好的音频"**：声音是**逐音实时合成**的——谱面每颗音触发一次采样播放，力度与发声时长都来自
  参考演奏；机器停在哪一秒，声音就停在哪一秒。它跟"播一条混好的音轨"的区别，就是"演奏事件流"和"成品音轨"的区别。
- **但确实不是音符盒本体发声**：音源是 mod 的引擎，音符盒目前只是机器上的实体零件。用户问得对。

mod 从一开始就**是按"音符盒增强"设计的**：`NoteBlockMixin` 注入 `NoteBlock.onSyncedBlockEvent`，
红石触发音符盒的那一刻掐掉原版声音、换成无损采样（力度/时值/音色都由谱面决定）。所以问题不是"想不想走"，
而是**音符盒在当前布局里根本触发不了**。这一轮把这件事一次查清。

## 实验（无头副本服，`-Dnbmachina.selftest=true`，NbmachinaSelfTest 的音符盒触发矩阵）

方块事件要下一 tick 才派发，所以每个用例"布置 → 隔一拍读计数"。四个用例只差**触发位在哪**：

| # | 布置 | mixin 事件 | 结论 |
|---|---|---|---|
| ① | harp + 上方空气 + 红石块在**水平侧面** | **1** | ✅ 触发机制本身通（mixin 生效、命令链正常） |
| ② | snare（非基座类乐器）+ 红石块在**正上方** | 0 | ❌ 上方不构成有效充能位 |
| ③ | 石头甲板（导体）+ 红石块在**甲板下方** | 0 | ❌ 隔着方块"间接充能"对音符盒无效 |
| ④ | harp + 红石块在**正下方** | 0 | ❌ 下方同样不行 |

**结论：只有"水平相邻"的红石块能触发音符盒；上下方向都不行。**

这与 M3-21 §6 的历史结论吻合（当时把触发位放在音符盒正上方 y+2，所以机器从来没响过），
也解释了为什么后来改成数据包逐音调 `/nbm playat`：那是**在密集单排布局下唯一能让整首歌发声**的做法。

## 要回到"音符盒本体发声"，需要做什么

每个音符盒**腾出一个水平相邻格子**当触发位（相邻红石块），数据包在该音的时刻放/拆红石块：

```
音符盒行：   [♪][♪][♪][♪] …
触发道：     [■][■][■][■] …   ← 与音符盒行水平相邻（Z+1），逐音放/拆红石块
```

- 机器体积：多一条触发道（沿 Z 加一排，或改成两行交错），长度不变；
- 数据包：把 `nbm playat` 那一行换回"放红石块 → 音符盒响 → mod 接管音色"；
- 时机精度：仍是服务器刻级触发（与现在同量级，不退化）；`/nbmc play` 的客户端 1ms 级路径不受影响；
- 附带好处：**没装 mod 的玩家能听到原版音符盒声**（真正的红石音乐机），装了 mod 才是无损音色。
- 代价：布局与 196 个结构要重生成、数据包重发、`/nbmc samples` 之外还要重跑一遍验收（约半天工作量）。

## 现状与选项

- **现状（A）**：机器负责灯/粒子，声音由 mod 引擎逐音播放（`/nbm playat`）。音质最好、数据最省事，
  但"音符盒不发声"。
- **改造（B）**：加触发道，让音符盒本体触发、mod 接管音色。更贴近"音符盒增强"的定位，
  也能让没装 mod 的人听到原版声音。工作量约半天，机器体积大一圈。

两条路可以并存：数据包同时保留 `#snd` 守卫（=0 时走 mod、=1 时走音符盒本体），由玩家切换。
