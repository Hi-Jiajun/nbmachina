# nbforge 设计（讨论纪要 v0.1）

> 三组讨论产出：`DISCUSSION-A-product.md`（产品）、`DISCUSSION-B-architecture.md`（架构，进行中）、
> `DISCUSSION-C-music.md`（音乐）。本文是汇总后的设计，**待用户批准后才开始实现**。

## 一、目的（一句话）
把「一首歌」变成一台**在 Minecraft 里由实体音符盒真实演奏**的机器 —— 并且**可验收、可回退、可复现**。

## 二、成功标准（全部可量化）
1. 一条命令后 ≤60 秒听到第一个音，日志 0 条 ERROR
2. 触发数量与数据**差 0**（全曲 3099 音，逐刻对照）
3. 演奏期间 MSPT ≤ 50，且推进速率 = 设定刻率
4. 通过 10 条「人耳验收清单」（C 组给出）
5. 一键回退后，与备份**逐格差异 0**

## 三、范围
**做**：单人 Java 1.21.10 · 输入 = MIDI/转谱 CSV + 原曲 WAV · 布局 = 直线 / S 形折返 / 逐段爬升 ·
实体音符盒发声 · 灯光跟随 · 自动分段强加载 · 刻率方案 · 一键 redo/undo/report · 无头服务器验收

**不做**：基岩版 · 多人服务器 · 跨版本适配 · 音频版权处理 · 音频自动转谱（我们只做"用音频校正"）·
GUI · 强制依赖模组（模组作为可选增强）

## 四、三组讨论的关键结论

### A 产品视角
- 用户全程只需记 **3 条命令**：`styx:redo` / `styx:undo` / `styx:report`
- 五步 node 流程应合并为一条 `build`；所有音域/剖面问题必须在**离线阶段**暴露，不进游戏才发现
- 需要 `styx:doctor` 自检（函数加载、刻率、强加载、触发位、计数）
- **实测发现真 bug**：`play/start`、`play/stop`、`play/reset` 三个函数**加载失败**——
  它们恰好是唯一含 `tick rate` 的文件，而 `/tick` 需要权限等级 3、数据包函数只有等级 2
  ⇒「一条命令跑完」目前不成立。修法：`/tick rate` 由用户在聊天里敲，或由 `redo` 明确提示

### B 架构视角（结论待补全）
- 流水线五步：analyze → arrange → layout → emit → verify，每步幂等、可单独重跑
- 播放器派发：现状 **279 个分桶函数/刻**（≈2.8 万命令/刻）偏重，改为层级派发（对数级）
- 刻率：演奏期 100 tps、结束恢复 20；另提供"不改刻率"的降级模式（节奏会有 ±25 ms 抖动）

### C 音乐视角（最重要，推翻了此前的假设）
- **输入数据本身不可信**：旋律横跨 5 个八度、贝斯只有 **30.8%** 的音落在音频证据支持的那个八度上；
  **276 处撞格**（同声部重复 157 处 → 必然漏音）；音级被吸附到单一音阶（C# 自然小调），
  另外 5 个音级基本被抹掉；MIDI 里**没有力度、没有时值**（全 velocity 90、全 0.05 拍）
- **"错音"来自输入，不是折叠算法**：输入自身就有 113（旋律）+157（贝斯）对"相邻两音相差整数八度"的错误
- **必须先做"用原曲音频逐音标定八度"**：旋律 98.3% 落在 ±1 八度内（可直接校正），贝斯必须重做
- 声部 → 乐器 → 音区建议：旋律 harp 12–24 · 内声部 harp 0–11 · 低音 bass 0–12 ·
  打击乐固定行 0（石类→basedrum、玻璃类→hat），合起来可用音区≈4 个八度
- 力度换口径：现在的"0.12 s 混音 RMS"是**混音响度**，应改为"该音级在该八度上的窄带能量"
- 节奏网格已验证：0.12 s/步（278.4 s vs 原曲 281.4 s，差 1.1%）；但 `audio-tempo.mjs` 的输出不可信（需重写）

## 五、里程碑
| 里程碑 | 内容 | 验收 |
|---|---|---|
| **M0 修数据** | 音频八度标定 + 去撞格 + 音级恢复 + 力度换口径 | 贝斯八度命中率 >90%；撞格 0；notes 数据与音频 chroma 对齐 |
| **M1 播放器架构** | 层级派发 + tick rate 修复（含 `doctor`） | 一条命令可跑完；279→≤20 次调用/刻；MSPT ≤ 50 |
| **M2 编曲增强** | 声部/打击乐/力度曲线/延音近似（同音重复） | 听觉清单第 1~6 条通过 |
| **M3 验收闭环** | 无头全曲跑 + 逐刻计数对照 + undo 差异 0 | 成功标准 2/3/5 全绿 |
| **M4 音色（可选）** | 资源包 MVP（钢琴/弦乐/鼓） | 主观听感提升，不改机器结构 |

## 六、需要你拍板的四件事
1. **重做八度标定**（会改变机器上的音符分布 → 需要跑一次换音）——这是"错音"的根因，强烈建议做
2. **加打击乐层**（basedrum/hat 固定行）——能显著提升"有劲/像原曲"的听感，但机器上会多一类音符
3. **刻率 100**（世界会被加速 5×，作物/生物/红石一起加速；单人无妨，结束自动恢复 20）
4. **资源包音色**（可选，工作量较大；不做也不影响功能闭环）

# v0.2 · 按用户反馈修订（2026-09-14）

用户提出 7 条方向性意见，全部采纳并固化为设计约束。

## ① 模块化（可单独调用 / 可被更好的实现替换）
每个模块 = **独立 CLI + 稳定的文件接口（文件进 / 文件出 + JSON 报告）**，互不假设对方由本项目实现：

| 模块 | 输入 → 输出 |
|---|---|
| `ingest` | 音频/MIDI/MusicXML/PDF → `project.json`（规范格式）|
| `analyze` | `project.json` + 音频 → 分析报告（速度 / 音域 / 八度证据 / 力度证据）|
| `arrange` | `project.json` + 分析报告 → `score.json`（音符盒可演奏谱面）|
| `layout` | `score.json` + 世界地形 → `layout.json`（机型 / 剖面 / 开槽）|
| `emit` | `score.json` + `layout.json` → 数据包（结构 / 播放器 / 灯光 / 安装脚本）|
| `verify` | 数据包 + 原曲 → 客观指标 + 评分报告 |
| `deploy` | 数据包 → 存档（含备份与回退）|

任何一步都可单独跑、可替换（例如 `analyze` 换成更准的 OMR 工具，或 `layout` 换成多轨机型）。

## ② 输入：以「工程文件」为基底，标准格式优先
**内部规范 = `project.json`（超集）**，其字段 1:1 映射到以下**可商用、权威、广泛使用**的公开标准：

| 层 | 采用标准 | 理由 |
|---|---|---|
| 乐谱层 | **MusicXML**（W3C 社区标准）| 音符/时值/声部/连音/力度记号；MuseScore、Finale、Sibelius、Dorico 全支持 |
| 演奏层 | **SMF（MIDI 标准文件）** | 事实标准；时间轴 / tempo map / velocity / 多轨 |
| 制作层（可选）| **DAWproject**（开放工程交换格式）| 需要混音/自动化时使用；开放规范 |

输入通道：MIDI · MusicXML · **PDF 乐谱（经 OMR，如开源 Audiveris）** · 音频（只用于**校正与对比**，不做自动转谱）· 直接手写/编辑 `project.json`。
**一切皆可编程、可自定义修改**（JSON Schema + 校验器；每步产物都是纯文本）。

## ③ 编曲：两条并行输出（同一谱面、两条渲染路径）
- **后端 A「增强模式」**：配合自研音符盒增强 mod，让音符盒像电钢琴/软音源一样映射**任意音色 + 独立力度 + 延音**，最大程度还原原曲；
  **但保留 MC 音符盒特色**（方块视觉、粒子、红石灯反馈、木质手感），明确**不做**"直接播放原曲音频"这种伪还原。
- **后端 B「原版兼容模式」**：在 2 个八度 + 原版 harp/bass + 打击乐映射下做兼容化编曲，尽量少损失原曲色彩。

两者共享 `arrange` 的同一份 `score.json`——**同一谱面，两种渲染**。

## ④ 音符盒增强 mod（自研）

> **2026-09-15 起：这条是主路径**（用户撤销了"不强制依赖模组"的约束）。资源包只作为可选降级副本；
> 无损母版 / 多声道 / 真·力度延音 / 直接读谱面调度都在 mod 里实现。原版音符盒那套音色**不需要复刻**——
> mod 直接引用游戏内置 `SoundEvents.BLOCK_NOTE_BLOCK_*` 就是原版音（机制亦可完整复刻）。
Fabric mod（1.21.10，自研代码、MIT）：自定义音色绑定 · 每音力度/延音 · 演奏可视化（粒子/灯）· 与数据包通过约定接口通信。
不依赖第三方 mod，避免许可与侵权风险。

## ⑤ 保真契约：工程文件怎样，实际效果就怎样
- 每一步变换都必须**显式、可量化、可回归**：模块输出 `report.json`（本步做了什么近似 / 丢弃了什么 / 指标是多少）
- 抽象化处理原则：**能对上的就对齐（可测），对不上的必须写进报告**（不允许静默近似）
- 回归方式：同一 `project.json` → 同一 `score.json` → 同一数据包（字节级可复现），效果差异全部来自显式声明的降级项

## ⑥ 验证：客观 + 主观综合评分
`verify` 输出综合分（权重可配，默认客观 70% / 主观 30%）：

- **客观（对原曲音频）**：起音对齐 F1 · chroma/音级相似度 · 八度命中率 · 力度包络相关 · 漏音率
- **主观（人耳清单）**：旋律走向 / 重音 / 低音可辨 / 段落疏密 / 音色自然度 等 10 条，1~5 分打分表
- 目标：把"好不好听"从主观争论变成**可追踪的分数曲线**（每次改动都能看到分数变化）

## ⑦ 音色资源：自主创建，且不许廉价电子味
- 优先级：**自录/自合成**（本机有 C01U Pro 电容麦，可采样真实乐器）> 严格许可的素材（CC0/公有领域，须标注）
- 每件乐器要求：多层力度（≥3 层）+ 循环点 + 自然衰减包络；避免廉价 GM 音源的"塑料感"
- 交付形态：自研资源包（命名空间独立，不与任何第三方资源包冲突）
