# 讨论 A · 产品与用户视角（角色：产品负责人）

> 先说结论（只读这段也能决策）：
> 1. **定位**：nbmachina 是「把一首歌变成一台自己会演奏的实体音符盒机器」的一键工具链；
>    第一版只服务一个用户在**单人 Java 存档**里把整首歌**完整放完**。
> 2. 当前最大的产品缺口**不是音色/美化**，而是「一条命令跑完」这句承诺还没兑现：
>    无头服务器上 `styx:play/start`、`play/stop`、`play/reset` **根本没加载成功**
>    （日志实证，见 §4.2），所以「重做完成」之后音乐不会响。
> 3. 因此 MVP 的完成定义必须先钉死在**能量化验证**的三件事：能跑通、不漏音、不卡；
>    音色、视觉美化全部排到之后。
> 4. 一切承诺都要能在无头服务器上被脚本验证——不接受「听起来差不多」。

---

## 1. 目标用户与目标

### 1.1 一句话定位

**给会玩 Minecraft Java 的人，用一条命令把「一首歌的转谱数据 + 原曲音频」变成一台
真正由实体音符盒发声的音乐机，并让人能确认它真的播放完整。**

### 1.2 用户是谁

| 层级 | 用户 | 特征 | 对产品的要求 |
|---|---|---|---|
| 第一用户（现在） | 作者本人 | Windows + PCL2 + 1.21.10-Fabric，单人存档 `Styx Helix`；会敲命令、会跑 node，但**不愿意手工挪文件** | 一条命令、失败能看懂、能回退 |
| 目标用户（下一步） | 想做「红石音乐」投稿的人 | 会开作弊、会复制数据包、会敲 `/function`；**不会读代码** | 双击装包 + 2~3 条命令 + 出错提示 |
| 明确不服务 | 服务器管理员、跨版本玩家、基岩/移动端 | — | 见 §6 |

### 1.3 三条成功标准（可验证）

1. **一条命令**：干净存档里敲 `/function styx:redo`，**60 秒内听到第 1 个音**，
   期间服务器日志 **0 条 ERROR / 0 条 `Unknown function`**。
2. **不漏音**：在刻 `T` 采样时 `#hits` 等于数据里 `tick ≤ T` 的音数（**差 0**）；
   全曲 **3099 个音**（bass 1360 / harp 1739）在 tick `27840` 时全部触发。
3. **不卡**：播放期间 **MSPT ≤ 50**（即推进 ≥ 20 tps），且实测推进速率 = 设定刻率。

> 为什么不用「好听」「好看」当成功标准：这两条无法脚本验证，只能作为**上线后的加分项**。

### 1.4 为什么这件事值得做

声音来自**实体音符盒被红石充能后自己发声**，不是 `/playsound` 播音频。
这是可拍视频、可被观众判定的硬指标（听众能看出是真机演奏），也是本项目和
「放一段音频」类做法的分界线。产品叙事必须一直围绕这一点，美术与音色都不能破坏它。

## 2. 功能清单（按用户看到的行为写，不写技术词）

### MVP（不做完就不算能用）

| 功能 | 用户看到的行为 |
|---|---|
| 一键重做 | 敲一条命令，机器自动补齐/修好，约 1 分钟后自己开始演奏 |
| 真机演奏 | 站在机器旁能听到**音符盒自己**响，不是背景音乐 |
| 灯光跟随 | 每颗音对应的灯亮起，肉眼能跟上旋律走向 |
| 自动收尾 | 演奏结束自己停下、灯全灭、不再占用世界加载 |
| 一键回退 | 一条命令把地形和机器底座还原成原来的样子 |
| 监听模式 | 打开后**走远也能听到**（每个音会在你脚下再响一遍） |
| 进度/自检 | 一条命令报出「已播多少音 / 当前时刻 / 监听是否开」 |

### 次要（MVP 之后、值得做）

- **力度变化**：能听出强弱（现在只在监听模式里有效，实体音符盒音量固定）。
- **长机器的自动分段加载**：机器 2352 格跨了 400 多个区块，需要自动切换加载范围。
- **试听前 N 秒**：不想每次等整首，先确认"开头对不对"。
- **错音清单**：告诉用户"第 X 段第 Y 个音因为音域限制被折回"。

### 未来（不影响 MVP 验收）

- 资源包音色（钢琴/弦乐/鼓），摆脱只有 harp/bass 两种音色。
- 一键安装（双击就装进存档，不需要手动复制目录）。
- 换歌即用：现在是焊死的 `styx` 数据，目标是换一份转谱数据就能出生新机器。
- 多轨/折返机型；模组联动（把力度真正写进音符盒）；图形界面。

## 3. 典型使用流程（现状 vs 目标，手动 vs 自动）

前提：用户有一首歌的**转谱数据**（CSV：step/instrument/midi/音高）和**原曲音频**（wav）。

### 阶段 0 · 装包

| 用户动作 | 工具动作 | 是否应自动化 |
|---|---|---|
| 双击一个安装脚本 | 自动找到 `saves/<存档>/datapacks` 并复制数据包 | **必须自动化**。现状 `install_styx_pack.ps1` 把路径写死成 `C:\Program Files\PCL2\.minecraft\versions\1.21.10-Fabric 0.19.5\saves\Styx Helix`，换启动器/存档就失效 |
| 在存档里开作弊（或自己给自己 OP） | 无 | **必须手动**（这是游戏安全设置，工具不该代劳） |

### 阶段 1 · 生成（现在在电脑上跑 5 条 node 命令）

| 用户动作 | 工具动作 |
|---|---|
| 现在：按 README 依次跑 `analyze → arrange → layout → emit → test` 五步 | 分析音频/转谱 → 音高折叠 → 生成机器剖面 → 生成数据包（结构 + 播放器 + 灯光 + 一键链）→ 无头验收 |
| 目标：跑一条 `/nbm build 我的歌.csv 我的歌.wav` | 同上，并在出错时说清"哪一步、哪个文件、怎么修" |

**这一步最重要**：它是**离线生成**，可以在没有游戏的情况下失败、重试、回退。
所有能在这步发现的问题（音域超限、段剖面被山挡住、转谱缺音）都不应该拖到游戏里才暴露。

### 阶段 2 · 进游戏建造

| 用户动作 | 工具动作 | 是否应自动化 |
|---|---|---|
| 进存档、敲 `/function styx:redo` | 修地形 → 分三段强加载 + 替换音符 → 打开监听 → 自动开始播放 | 应自动化（现在已经是一条命令了，但见 §4.2：**这条链现在跑不通**） |

### 阶段 3 · 演奏

| 用户动作 | 工具动作 |
|---|---|
| 站在机器旁听（或开监听走远） | 刻率自动提高、强加载自动分段切换、灯跟随、结束自动停 |
| 想知道状态时敲 `/function styx:play/report` | 报出已触发音数 / 当前刻 / 监听开关 / 钢琴与贝斯各播了多少 |

### 阶段 4 · 后悔了

| 用户动作 | 工具动作 |
|---|---|
| 敲 `/function styx:undo` | 依次还原挡墙、机器底座、地形（`undo_wall` → `undo_deck` → `undo_terrain`） |

### 流程的判定标准

**用户需要记住的命令 ≤ 3 条**（`redo` / `undo` / `report`），
其余（坐标、段剖面、刻率、加载范围、回退快照）全部由工具算出来。
现在需要用户记的隐性知识太多（"要在哪个存档、要开作弊、要跑 install 脚本"），这正是要削掉的部分。

## 4. 失败与回退

原则：**任何失败都必须在 3 秒内让用户看懂"哪里错了 + 敲哪条命令"，并且有一条一键回退。**

### 4.1 失败清单

| 失败 | 用户看到什么 | 用户动作 |
|---|---|---|
| 敲了命令但没反应/音乐不响 | `[Styx] 重做完成…3 秒后开始播放` 之后**静默** | 敲 `/function styx:play/report` 看 `已触发音符数` 是否为 0；为 0 → 判定"播放没起来"（自检命令应直接给出这句话） |
| 漏音（区块没加载 / 强加载没覆盖） | 某几段整段不响 | 工具应报出**哪一段、哪个 x 区间**没加载；`/function styx:play/stop` 后重跑 redo |
| 触发位被挡（音符盒上方有方块） | 个别音不响 | 验收脚本报"被挡住的触发位坐标"；`/function styx:undo` 后重来 |
| 穿地形（机器插进山体） | 音轨某段埋在地下 | 现在靠逐段剖面 + 局部开槽规避；真出事就 `/function styx:undo` |
| 卡顿 / 播放拖慢 | 音乐变慢、灯一顿一顿 | 工具应输出 MSPT 与推进速率；降级方案：降低刻率或减少同刻发射数（见 §7，需要 B 给方案） |
| 听不到（走远了 / 低频贝斯放不出） | 远处就是没声 | 敲 `/function styx:play/monitor_on`（监听模式） |
| 错音（八度折叠回折） | 个别音"跳"了一下 | **物理限制，不修**；由工具输出"错音清单"，写进已知限制 |
| 数据包函数加载失败 | 游戏里 `Unknown function styx:play/start` | **必须先修**，见 4.2 |

### 4.2 本次核查发现的两个真实问题（有日志实证，建议优先修）

**问题 1：三个播放函数在服务端加载失败，导致「一键重做」实际不会开始播放。**

证据：`C:\Users\hiliang\Documents\minecraft\testserver\v3test.log`

```
[23:49:17] [ServerMain/ERROR]: Failed to load function styx:play/reset
[23:49:17] [ServerMain/ERROR]: Failed to load function styx:play/stop
[23:49:17] [ServerMain/ERROR]: Failed to load function styx:play/start
    Whilst parsing command on line 11 / 7 / 9: Unknown or incomplete command
...
[23:50:04] [Server thread/INFO]: Unknown function styx:play/start
[23:50:26] [Server thread/INFO]: Unknown function styx:play/stop
```

这三个文件正是**唯一三个含 `tick rate` 命令**的函数（`start` 第 9 行、`stop` 第 7 行、
`reset` 第 11 行；其余 279 个分桶函数和 `monitor_*`、`report` 都正常加载）。
产品后果：`styx:redo` 最后一步 `schedule function styx:play/start` 调用的是一个不存在的函数，
用户看到"重做完成"却听不到声音——**这就是"一条命令跑完"当前兑现不了的原因**。

**问题 2：「216 vs 68」大概率是口径/时序问题，不是漏音。**

证据：同一次运行 `#t = 1684`、`#hits = 216`；而 v3 数据里 `tick ≤ 1684` 的音**恰好是 68 个**。
同时验收脚本是先读 `#t`、**600 毫秒后**才读 `#hits`（刻率 100 时相差约 60 刻），
且 `start` / `reset`（负责把 `#hits` 清零）加载失败 → `#hits` 很可能带着上一轮的旧值没被清。
产品后果：**验收脚本目前不能用来做"不漏音"的判定**。修法很便宜：先断言所有函数加载成功、
清零后在同一刻采样，然后逐步对齐累计数。

补充证据：`testserver\redotest.log` 里跑完 `styx:redo` 后 95 秒 `#t` 只到 485，
再过 6 秒仍是 485（推进停下/没起来）——§5 的第 3 条标准就是为了把这类"看起来在跑"的现象量化。

## 5. 验收标准（5 条，都可量化、可脚本化）

1. **一条命令能跑通**：干净存档 → `/function styx:redo` → 60 秒内听到第 1 个音，
   日志中 `Failed to load function`、`Unknown function`、`ERROR` 各 **0 条**。
2. **不漏音**：在同一刻采样，`#hits == 数据中 tick ≤ T 的音数`（**差 0**）；
   终态 `T = 27840` 时 `#hits = 3099`（bass 1360 / harp 1739）。
3. **不卡**：播放全程 **MSPT ≤ 50**，实测推进速率 = 设定刻率（±0%）。
   现状是**每刻调用 279 个分桶函数**（约 2.8 万条命令/刻），这一条**大概率不达标**，
   必须先做层级派发（需 B 给方案），在此之前不得对外宣称"可用"。
4. **抽样正确**：随机抽 3 段 × 3 个音，核对「音符盒位置 / 音色 / 灯 / 触发位为空」四项
   与数据一致（现有抽查：`V3_NOTE_OK`、`V3_UNDER_OK`、`V3_LAMP_OK`、`V3_TRIG_FREE_OK`）。
5. **可回退**：`/function styx:undo` 之后，抽样区域与备份存档逐格比对，**差异 0**。

## 6. 不做什么（明确划界，避免摊大饼）

- **不做基岩版 / 移动端 / 主机版**：命令与方块行为差异太大。
- **不做多人服务器 / Realms 支持**：刻率、加载范围、权限都会污染别人的世界。
- **不做跨版本兼容**：只钉 1.21.10（`pack_format 88`）。
- **不处理音频版权**：只接受用户自己的转谱数据与音频，工具不内置、不下载任何乐曲。
- **不做音频→转谱的自动转录**：转谱质量决定成品质量，这块交给专业工具；
  本项目只接"已经转好的谱"（社区经验：音频转录必然有错音）。
- **不依赖模组**：`NoteBetter` 这类只作为可选增强，缺了它必须照常能播。
- **MVP 不做 GUI / 启动器集成**：先保证命令行 + 数据包跑通，再谈包装。

## 7. 本组对其他两组的要求（产品验收口径）

**给 B（架构）**

- 一条命令链里**不允许**再出现需要更高权限、只能在聊天框里敲的命令——这次踩的就是 `tick rate` 的坑；
  凡是要用户在聊天框手动敲的东西，都要在文档里写成"用户动作"，不能藏在函数里假装自动化。
- 需要一个 `/function styx:doctor` 自检：把所有函数是否加载成功、强加载范围、刻率、
  `#hits/#t` 一致性做成一条命令的输出（产品上这是"失败能看懂"的地基）。
- 播放推进速率与 MSPT 必须可观测（写进 `report`），否则 §5 第 3 条无法验收。
- 层级派发重构后必须**保持 `#hits` 语义不变**（每触发一颗音 +1），否则历史数据无法对照。

**给 C（音乐）**

- 需要一份「错音清单」：哪些小节、哪个声部、因为音域限制被折回——A 才能把它写成用户手册里的"已知限制"。
- 需要一份听感验收清单（人耳可做、不需要专业设备），A 会把它作为 §5 之外的**人工复核**补充。

**给全体**

- 任何新承诺，先问一句：**这条能不能被无头服务器脚本验证？** 不能的，就写成"未验证/已知限制"。
