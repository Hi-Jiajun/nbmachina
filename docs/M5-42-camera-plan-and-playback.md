## 1. 用户报的"成片有些卡顿"

**结论：文件本身不卡，卡在播放端。**三条硬证据（都对 `StyxHelix_audio.mkv` 与原始导出的 `StyxHelix.mkv` 做过）：

| 检查 | 结果 |
|---|---|
| 视频码流逐包对比 | `ffmpeg -map 0:v -c copy -f md5` → 两文件都是 `f1630f2c3783f4e5ab049a66889681b2`（合轨只加音轨，一帧没动） |
| 时间戳节奏 | 34027 帧、34027 个**互不重复**的 PTS，间隔只有 8ms / 9ms 两种（= 严格 120fps，无丢帧/重复帧） |
| 内容运动 | 全片逐帧差分扫描（160×90 灰度，28 万帧差）：**0 帧**低于局部中位的 25% —— 没有任何"冻帧/顿点" |

那么卡顿来自播放链：**4K / 120fps / 10-bit HEVC（Main 10）/ 平均 ~140 Mbps / HDR10（bt2020+PQ）**。
这种码流必须走**硬件解码 + HDR 直通**，否则：

* 播放器回落软解 → 4K120 10-bit 软解不可能实时，表现就是一顿一顿；
* 播放器不认 PQ → 会先 tonemap 再输出（发灰）或反复重算，也会卡；
* 60Hz 屏 + 帧率匹配不好 → 120fps 内容被"2 帧 1 显"错配，看到规律性抖动。

**对照实验（已生成）**：`C:\Users\hiliang\Videos\StyxHelix_60s_1080p60_SDR.mp4`
（60–90s，1920×1080 / 60fps / H.264 8-bit / bt709 —— libplacebo hable tonemap，28 MB）。
这条要是**顺**，就说明是上面那套 4K120 HDR 播放链的问题（换播放器硬解/HDR 直通即可）；
要是**也卡**，那才轮到查盘/CPU/显卡驱动。

## 2. 原来那 4 个相机关键帧的问题

原编辑态只有 4 个 keyframe（tick 74 / 134 / 146 / 5745）：

* 134 → 146 两个点只隔 **0.6s**，x 却从 −48.13 跳到 −18.17 → **30 格 / 0.6s ≈ 50 格/秒**的甩镜（比播放头 8.33 格/秒快 6 倍）；
* 146 → 5745 一个 SMOOTH 段横跨 **280 秒**，等于"全程匀速滑行"，跟歌曲段落没有任何关系 —— 这就是"关键帧不贴合歌曲进度"的根因，不是操作姿势问题。

## 3. 现在的方案：`tools/nbm-camera-plan.mjs`

相机位置 = **播放头 − 滞后（lag）**，播放头 `x = 8.3341·t − 32.784`（t = 谱面秒，+3.3458s 换成回放 tick），
所以"跟着歌走"是算出来的，不靠手拖。方案按 `build/dynamics-sections.json` 的 19 段响度 + M5 十场表打点：

| 段落 | 手法 |

| S0 空河 → S1 首句 | 中景缓降（y 121.5→116.8，lag 26→21），开场卡片锚屏不动 |
| S2 乱钟 / 落砂 | 压低贴近（y 115.4、lag 15、pitch 6°）——俯看和弦与涟漪 |

## 5. 开场静止（2026-09-25 用户反馈后修订）

用户："开场我想要它暂时不要动，等封面和文字消失之后再前进，不然观感上会觉得封面和文字在抖动。"

开场卡片时序（`StyxShow` 常量，全部相对谱面 0s）：封面淡入 0.35s / 文字淡入 0.70s；**2.30s 起一起淡出，0.70s 后即 3.00s 完全消失**。
卡片是**屏幕锚定**的（每刻按当前眼位重算 26 颗粒子的世界坐标），镜头一动粒子锚点就重烘 → 观感上就是"卡片在抖"。

修法（已写进编辑态）：

* 谱面 **0 → 3.20s 机位完全不动**：两个关键帧位置逐位相同（x −58.784 / y 119.0 / z 2.5 / pitch 0），
  第一帧插值类型用 **HOLD**（`SidedInterpolationType.HOLD` → 整段保持左值），保证不是"缓入"而是真的静止；
* 3.20s 之后才起步，用 ~11 格/秒（播放头 8.33 格/秒）缓加速把滞后从 53 格收回 21 格，
  到 22.94s（S1 首句）恢复常规巡航 —— 全段最大机位速度仍是 13.15 格/秒。
